# 拜訪備忘與日曆：下次要帶什麼、上次講過什麼

2026-10-07

業務講完報價，常會順口說這次跟客戶談了什麼：「下次記得帶骨營的 DM 過去」「跟店長說了 Premium 小口買 22 送 1」。
現在這些話只留在逐字稿裡，下次去這家時沒有地方看得到。這次加「拜訪備忘」：錄音時 AI 一起抽出來，業務也能手寫；
下次去這家時客戶檔案與今日路線看得到，有日期的放上日曆。

## 為什麼做

- 拜訪的五個欄位裡，「承諾」只記一件有期限的事；要帶的輔銷物、跟客戶講過的促銷沒有地方記。
- 下次去之前，業務要自己翻逐字稿才知道上次答應帶什麼、講過什麼條件。
- 首頁只有今天的行程，沒有一個地方看得到哪天要帶什麼、哪天講過什麼。

## 已定案的決定

1. **兩種備忘**：「要帶的」（DM、POP、海報、試用包、樣品、衛教單張、比價表…）與「講過的」（跟客戶講了哪些促銷、實銷、搭贈、活動條件）。
2. **全部當紀錄，不用勾**：下次去這家時只列「最近一次有備忘的拜訪」記下的那幾則，加上那次之後手寫的；有新的就蓋過舊的。
3. **日期**：
   - 要帶的：業務講了哪天就放那天；沒講但這次拜訪有追蹤日，放追蹤日；兩個都沒有就不放上日曆，只在「下次去這家」出現。
   - 講過的：放講的那天（拜訪日；手寫的預設是寫的那天，可以改）。
4. **日曆與客戶檔案兩邊都看得到**；今日路線點開某一站的小卡也列這家的備忘。
5. **另開一張表**（`customer_note`），錄音與手寫的都寫進這張表，日曆、客戶檔案、今日路線都讀它。不放進頻道的記憶看板：
   看板要等熊熊滾整理、內容是 AI 改寫的，而且整區看得到，報價與議價條件會外流。
6. **權限跟報價一樣**（`SHARING_LEVEL["quote"]`，SELF）：負責人與他的主管看得到、改得了，其他人跟這家客戶不存在一樣回 404。
7. **入口**：底部分頁已經五個，不再加；點首頁紫色橫幅上的日期進日曆（`/calendar`），客戶檔案多一區「下次去要記得」。
8. **系統日**：日曆打開在 `app_today()`（決賽日 10/28）那個月，「今天」標的也是它，跟首頁同一個日期。

## 資料

`models.py` 改了，`schema_version` 的指紋跟著變，部署時重建資料庫（跟以往一樣）。

### `customer_note`

| 欄位 | 內容 |
|---|---|
| `id` | 流水號 |
| `customer_id` | 哪家客戶 |
| `user_id` | 誰記的：錄音來的是做這次拜訪的人，手寫的是寫的人（代理示範業務的帳號記實際寫的人） |
| `kind` | `bring`（要帶的）／`told`（講過的） |
| `text` | 內容，1～200 字 |
| `on_date` | 放在日曆的哪一天；要帶的可以是 NULL |
| `visit_id` | 從哪次拜訪來的，手寫的是 NULL；拜訪刪掉時一起刪（`ON DELETE CASCADE`） |
| `created_at` | 建立時間 |

- `CHECK (kind IN ('bring', 'told'))`、`CHECK (kind = 'bring' OR on_date IS NOT NULL)`、`CHECK (char_length(text) BETWEEN 1 AND 200)`。
- 索引：`(customer_id, created_at)`、`(on_date)`。

### 下次去這家（`services/customer_notes.next_notes`）

1. 找這家客戶最近一次「有備忘的拜訪」：`visit_id` 不是 NULL 的備忘裡，最後建立（流水號最大）的那一則所屬的拜訪。
2. 列出那次拜訪的備忘，加上手寫、建立在那次拜訪的備忘之後（流水號比較大）的。沒有任何拜訪來的備忘，就列全部手寫的。
3. 要帶的排前面，同種照建立的先後。用流水號不用 `created_at`：同一個交易裡建的幾則 `created_at` 一樣。

### 拜訪意向多一個欄位 `notes`

`visit_fields.schema.json` 加第六個欄位：

```json
"notes": {
  "description": "下次要帶的東西與跟客戶講過的促銷",
  "type": ["array", "null"],
  "minItems": 1,
  "items": {
    "type": "object",
    "additionalProperties": false,
    "required": ["kind", "text", "date"],
    "properties": {
      "kind": { "enum": ["bring", "told"], "description": "bring=下次要帶的東西，told=跟客戶講過的促銷或條件" },
      "text": { "type": "string", "minLength": 1, "description": "業務的講法，精簡成一句" },
      "date": { "type": ["string", "null"], "format": "date", "description": "要帶的東西業務講了哪天；沒講或講過的填 null" }
    }
  }
}
```

- `extraction.FIELD_KEYS` 加 `notes`，`sources` 也跟著要列（結構化輸出要求物件的欄位全部明列）。
- 假資料的拜訪補 `"notes": null`；測試語料沒寫 `notes` 的題目當作 null。
- `docs/visit-fields.md` 加一列與一條規則。

## 錄音

### AI 怎麼抽

`extraction.PROMPT` 加第 10 條：

> notes 收兩種：bring 是業務說下次要帶給客戶的東西（DM、POP、海報、試用包、樣品、衛教單張、比價表…）；told 是業務跟客戶講了哪些促銷、實銷、搭贈、活動條件。text 用業務的講法、精簡成一句。date 只在業務講了哪天要帶、或下次哪天去時才填（照第 3 條換算），講過的一律填 null。可以跟 commitment、intent 重複，例如「我答應下次帶比價表」兩邊都填。

| 業務說 | 抽出來 |
|---|---|
| 下次記得帶骨營的 DM 過去 | bring「骨營的 DM」，date null |
| 下週三再去，記得帶試用包 | bring「試用包」，date 下週三；follow_up_date 也是下週三 |
| 跟店長說了 Premium 小口買 22 送 1 | told「Premium 小口買 22 送 1」 |
| 店長抱怨補貨延遲三天 | notes null（是 complaint） |

### 確認頁

- 欄位清單多一列「備忘」，一行摘要寫「要帶：骨營的 DM、試用包（10/30）；講過：Premium 小口買 22 送 1」。
- 編輯：一列一則，選種類（要帶的／講過的）、內容；要帶的可以選日期。
- 跟其他欄位一樣，AI 整理出來卻對不到原文的會標出來請業務核對。

### 確認時寫進備忘表

在 `POST /api/visits/{id}/confirm` 的同一個交易裡（跟建追蹤提醒一起），不是回寫三套系統的一部分：

- 要帶的：`on_date` ＝ 這一則的 `date`，沒有就用這次的 `follow_up_date`，再沒有就是 NULL。
- 講過的：`on_date` ＝ 拜訪日（`local_date(visited_at)`）。
- `user_id` ＝ 這次拜訪的業務，`visit_id` ＝ 這次拜訪。

## API

都在 `backend/app/api/notes.py`，權限照「已定案的決定」第 6 條。

| 方法 | 路徑 | 內容 |
|---|---|---|
| GET | `/api/customers/{id}/notes` | `{ next: Note[] }`：下次去這家要記得的 |
| POST | `/api/customers/{id}/notes` | 手寫一則：`{kind, text, on_date?}`；講過的沒給日期就用 `app_today()` |
| PATCH | `/api/notes/{id}` | 改 `kind`、`text`、`on_date` |
| DELETE | `/api/notes/{id}` | 刪掉 |
| GET | `/api/calendar?month=2026-10` | 這個月有東西的每一天：`{ month, today, days: [{date, visits, notes}] }` |

- `Note`：`{id, customer_id, customer_name, kind, text, on_date, visit_id, created_at}`。
- 日曆看的是「行程主人」（`acts_as_user_id or id`，跟今日路線一樣）負責的客戶：
  - `visits`：那天確認過的拜訪 `{visit_id, customer_id, customer_name}`，照拜訪時間排。
  - `notes`：`on_date` 在那天的備忘，要帶的排前面。
  - `month` 格式不對回 422；沒給就是系統日那個月。
- 客戶檔案（`GET /api/customers/{id}/profile`）不另外塞備忘，頁面另外打 `GET /api/customers/{id}/notes`，今日路線的小卡也打同一支。

## 畫面

### 客戶檔案

「進門前三分鐘」下面一區「下次去要記得」：

- 要帶的、講過的分兩組，各自一個 lucide 圖示（`Package`、`MessageSquareQuote`），有日期的寫日期。
- 「記一筆」打開對話框：種類、內容、日期（講過的預設今天）。點已有的一則可以改或刪。
- 沒有備忘時只顯示一行「還沒有備忘」與「記一筆」。

### 今日路線

點圓鈕彈出的小卡，在理由下面多列這家的備忘（最多三則，多的寫「還有 N 則」），點小卡的按鈕進客戶檔案看全部。
小卡打開時才打 `GET /api/customers/{id}/notes`，載不到就不顯示這一區，不影響其他內容。

### 日曆（`/calendar`）

- 點首頁紫色橫幅上的日期進來；頁首有返回。
- 上面是月曆：月份、上一個月／下一個月、星期一到日七欄，每一格寫日期，下面一排小點：有拜訪、有要帶的、有講過的各一種顏色。系統日那一格框起來。
- 點一天（預設系統日），下面列那一天：
  - 拜訪：客戶名稱，點了進拜訪結果頁。
  - 要帶的、講過的：客戶名稱加內容，點了進客戶檔案。
  - 「在這天記一筆」：選客戶（自己負責的）、種類、內容，日期就是這一天。
- 手機寬度（390px）七欄不能橫向捲動。

## 示範資料

`catalog.NOTES` 手寫幾則，灌資料時寫進 `customer_note`（`visit_id` NULL、`user_id` U01），不動亂數，原本的假資料一筆都不變：

- 林昱辰負責的三四家客戶，有日期與沒日期的要帶的、決賽日之前幾天講過的促銷，日期都用決賽日往前或往後推幾天，換展示日也跟著走。

## 出錯時

| 情況 | 結果 |
|---|---|
| 看不到的客戶、別人的備忘 | 404 |
| 種類不是兩種之一、內容空白或超過 200 字、日期格式不對 | 422 |
| 講過的把日期清掉 | 422（講過的一定有日期） |
| 日曆的 `month` 不是 `YYYY-MM` | 422 |
| AI 抽出的 `notes` 不合 schema | 跟其他欄位一樣，整份欄位留白請業務手動填 |

## 測試

- 後端：
  - 確認拜訪時寫進備忘表：日期規則（自己的日期、追蹤日、都沒有；講過的用拜訪日）。
  - 「下次去這家」：新拜訪的備忘蓋過舊的、手寫的接在後面、沒有拜訪來的只列手寫的、排序。

- 前端：月曆排版（每個月第一天落在星期幾、補前後月的空格）、備忘一行摘要。
- 真的 Gemini：用上面表格的句子與幾句混著報價、承諾的話跑兩次，確認格式沒被拒、種類與日期抽得對。
