# 報價照促銷的口開：小口、中口、大口

2026-10-07

業務開報價單只有兩種講法：沒促銷是「Premium 眼藥水 20 盒」，有促銷是「幫我開小口 Premium 眼藥水」。
現在的報價只認得品項 × 數量，而且促銷的 20 個品項沒有交易紀錄，報價頁根本列不出來；拜訪錄音講「小口」，
AI 會抽成 1 盒。這次讓報價頁與拜訪錄音都能照「口」開，一口照活動價寫進 SAP 報價草稿。

## 為什麼做

- 一「口」是促銷的一個購買單位：買幾個、送幾個、另外加贈什麼，整口一個價（`promotion_item`）。
  同一個品項常分小口、中口、大口，口越大送越多。業務下單是照口下的。
- 報價頁只列這家近半年進過的品項（`GET /api/customers/{id}/quote-items`），促銷品項沒有交易，一項都不會出現。
- 拜訪錄音的下單意向是 `{product_text, sku, qty, unit}`，「小口 Premium 眼藥水」會變成 Premium 眼藥水 1 盒，
  SAP 收到的是 1 盒，不是買 22 送 1、$5,500。

## 已定案的決定

1. **報價的每一列只有兩種**：沒促銷的列是品項 × 數量，照這家的供貨價；促銷的列是某一口 × 口數，照每口售價。
2. **促銷的口不再打折**：整張報價的折扣只套在沒促銷的列。搭贈本身就是優惠，再疊折扣等於讓兩次。
3. **三種客戶都能選促銷的口，照活動價，不另外提示哪一種比較便宜**。連鎖的供貨價打 9 折，
   很多品項不走促銷反而便宜（Premium 眼藥水 $225／盒，小口攤下來約 $239），由業務自己判斷。
4. **報價頁與拜訪錄音兩條路都認得口**，寫進 SAP 報價草稿的方式一樣。
5. **一口在報價草稿裡還是一列**，在 `sap_quotation_draft` 加欄位記是哪一口、幾口、送幾個、這一列的金額；
   不另開一張表，也不把一口拆成付錢與送的兩列。
6. **加贈的其他品項**（骨粉、海藻鈣、葡萄籽…）**不拆成列**，只顯示搭贈說明原文：原始資料本來就只寫在說明裡，
   海藻鈣連料號都沒有。
7. **整張訂單的活動**（滿額贈、禮券）**不算**，報價頁顯示 PM 提醒原文給業務參考。
8. **哪一期**：系統日 `app_today()` 當天進行中的那一期，跟促銷頁、問答看到的同一份（`v_promotion.status = '進行中'`）。

## 資料

`models.py` 改了，`schema_version` 的指紋跟著變，部署時重建資料庫（跟以往一樣）。

### `sap_quotation_draft` 加的欄位

| 欄位 | 內容 |
|---|---|
| `promo_code` | 哪一口，FK `promotion_item.code`；沒促銷的列是 NULL |
| `packs` | 幾口；沒促銷的列是 NULL |
| `free_qty` | 同品送了幾個（每口送的 × 口數），預設 0 |
| `amount` | 這一列的金額，到分 |

- `CHECK ((promo_code IS NULL) = (packs IS NULL))`、`CHECK (packs IS NULL OR packs > 0)`。
- 促銷的列：
  - `qty` 是付錢的數量（每口買的 × 口數）。
  - `amount` 是每口售價 × 口數。
  - `unit_price` 記每口售價 ÷ 每口買的數量，到分，只供參考。
  - `discount_pct` 記 0。
- 沒促銷的列：`amount` 是折扣後單價 × 數量，`discount_pct` 記整張報價的折扣（跟現在一樣）。
- **金額要另外記**：有的口除不盡，例如骨營粉劑直走 7 盒 $3,100，一盒是 $442.857…，單價 × 數量對不回 $3,100。
  讀報價金額的地方一律加總 `amount`，不再自己乘。
- `discount_pct` 的註解從「每一列記同一個值」改成「這一列打的折扣」。
- 假資料（`generate.py`）的歷史報價草稿補上 `amount`＝單價 × 數量，其他新欄位留預設。

### 下單意向（`visit_fields.schema.json`）

`intent` 的每一項加 `promo_code`（`string | null`），列進 `required`：結構化輸出要求物件的欄位全部明列。

- 有 `promo_code` 時，`qty` 是口數、`unit` 是「口」，`sku` 是那一口的品項。
- 假資料的拜訪意向補上 `"promo_code": null`。
- `docs/visit-fields.md` 的 `intent` 那一列跟著改。

## 報價頁

### 畫面

常進品項下面多一區「這一期的促銷」：

```
常進品項（跟現在一樣，填數量，預設 0）            ← 這是一家獨立藥局，供貨價打 95 折
  魚油 30 入        [ 0 ] 盒    不列入
  人工淚液 15ml     [20 ] 瓶    $2,660

這一期的促銷  202610保藥特搭活動        [整張訂單的活動 ▸]
  獅王眼藥水
    Premium眼藥水 小口  買22送1            $5,500/口   [ 1 ] 口
    Premium眼藥水 中口  買57送4＋葡萄籽×2   $14,250/口  [ 0 ] 口
    Premium眼藥水 大口  買110送18＋葡萄籽×4 $27,500/口  [ 0 ] 口
    Premium眼藥水 不走促銷                 $238/盒     [ 0 ] 盒
  骨營 …

────────────────────────────
折扣 [ 2 ] %  只套在沒促銷的品項
合計 2 項                      $8,107
[ 開 SAP 報價草稿 ]
```

- 只列進行中的那一期；沒有進行中的促銷，這一區不顯示。
- 依品牌（`group_name`）分組，品牌底下依品項列出每一口：名稱、搭贈說明原文、每口售價、口數輸入框。
- **口數預設 0**，填了才列入，跟常進品項的數量一樣：全部預填的話，直接按送出就是一張十幾口的報價。
- **每個促銷品項多一列「不走促銷」**，照這家的供貨價填數量。這些品項沒有交易，不會出現在常進品項；
  不加這一列就開不出「Premium 眼藥水 20 盒」。品項已經在常進品項裡的，不重複列這一列。
- 「整張訂單的活動」點開是 PM 提醒原文，只給業務參考。
- 底部的合計＝沒促銷的列打折後的金額（算法跟現在的 `discountedTotal` 一樣）＋每一口的每口售價 × 口數。
  劃線的原價只在有折扣時顯示，算法同上但不打折。
- 有促銷的列時，折扣旁的說明寫「只套在沒促銷的品項」。
- 按鈕上的擋住原因，照現在的順序再加一條：有填折扣但沒有任何沒促銷的列，寫「折扣只套在沒促銷的品項上」。

### API

- `GET /api/customers/{id}/quote-promotion`（新的）：進行中的那一期，沒有就回 `null`。

  ```
  {
    name, pm_note,
    products: [{
      group_name, sku, name, spec, unit,
      supply_price,         // 這家的供貨價，給「不走促銷」那一列
      usual: bool,          // 已經在常進品項裡，前端不重複列「不走促銷」
      packs: [{ code, name, deal, buy_qty, free_qty, deal_price }]
    }]
  }
  ```

  讀 `v_promotion_item`，跟促銷頁同一份；權限跟 `quote-items` 一樣（`SHARING_LEVEL["quote"]`）。
- `POST /api/customers/{id}/quotes`：`items` 的每一項是 `{sku, qty}` 或 `{promo_code, packs}` 其中一種。
  - 一張最多 20 列（`MAX_QUOTE_LINES`），兩種合計。
  - 同一口只能列一次；同一個品項不走促銷也只能列一次；同一個品項的不同口可以同時開，也可以同時有不走促銷的那一列。
  - 回傳的 `QuoteLine` 加 `promo_code`、`packs`、`free_qty`、`deal`，`amount` 用這一列記下的金額。

### 簽核

- 關卡照折扣 % 決定，規則不變（`approvals.discount_level`）。
- 申請單的 `list_amount`、`amount`、`cost` **只算沒促銷的列**：簽核模型是用沒有促銷的單訓練的，
  把口算進去，折後毛利率會被拉偏。payload 另外記 `total_amount`（整張報價的金額）。
- 申請單的摘要（`oa.py`）：有 `total_amount` 而且跟 `amount` 不同時，寫
  「折扣 5%，打折的品項 NT$ 12,000，整張報價 NT$ 23,000」；其他情況照舊。歷史單沒有 `total_amount`，照舊。

## 拜訪錄音

### AI 怎麼抽

`extraction.build_prompt` 的品項表後面多一張「這一期的促銷」，一口一列：促銷品項編號｜sku｜名稱｜搭贈說明。
規則第 7 條後面加：

- 業務講到小口、中口、大口，或講到一口、兩口、某一口的搭贈（例如「買 11 送 2」、「直走」），
  而且對得到這一期唯一的一口，才填 `promo_code`，`qty` 是口數，`unit` 填「口」。
- 講了口但沒講幾口（「幫我開小口 Premium 眼藥水」），算 1 口。
- 沒講口就照現在的做法填品項 × 數量，`promo_code` 填 null。
- 講了口但對不到唯一的一口（「小口眼藥水」：Premium、40EXa、Pure 都有小口），`sku` 與 `promo_code` 都填 null，
  `product_text` 照原話。

| 業務說 | 抽出來 |
|---|---|
| 幫我開一個小口 Premium 眼藥水 | Premium眼藥水，小口那一口，1 口 |
| 金舒胃得大口兩口 | 金舒胃得，大口那一口，2 口 |
| 魚油 20 盒 | 魚油 30 入，20 盒（跟現在一樣） |
| 小口眼藥水 | 品項與口都空著，確認頁標紅請業務選 |

抽完在後端檢查：`promo_code` 不是這一期的口、或那一口的 sku 跟 `sku` 不同，就把 `sku` 與 `promo_code` 都清成 null，
讓那一項在確認頁標「缺少品項」。

### 確認頁

- 一行摘要（`field-format.ts` 的 `summarize`）：有口的寫「Premium眼藥水 小口 × 1 口（買 22 送 1，$5,500）」。
  名稱、搭贈與售價從促銷資料查；查不到就照現在的 `product_text × qty unit`。
- 編輯（`IntentEditor`）：選了品項，如果這一期有它的口，下面多一個選單「不走促銷／每一口（寫搭贈與每口售價）」。
  選了某一口，`unit` 改成「口」、數量欄的提示改成「口數」；改回不走促銷，`unit` 回到品項的單位。
  這一期的口從 `GET /api/promotions` 取進行中的那一期，不另開 API。
- 存欄位時後端檢查：`promo_code` 存在、而且那一口的 sku 跟 `sku` 相同，否則回 422。不再檢查期別，
  確認頁只會列出進行中的口。
- 送 SAP 的檢查不變：每一項都要有品項與數量（`missing_sap_details`）。

### 回寫 SAP

- `_write_sap`：有 `promo_code` 的項目照「資料」那一段記促銷的列，價錢讀 `promotion_item`；
  沒有的照現在用供貨價、不打折，另外記 `amount`。
- 回寫失敗後重送，就算那一期已經結束，還是照當初的那一口與價錢寫，不再檢查期別。
- 寫進 CRM 的意向摘要（`intent_summary`）不改：`product_text × qty unit`，有口的會是「小口 Premium 眼藥水 × 1口」。

## 讀報價的地方

- 客戶檔案的待處理事項（`customer_profile._open_quotes`）：促銷的列寫「Premium眼藥水(小口) × 1 口」
  （促銷品項名稱本來就把口寫在括號裡），金額加總 `amount`。
- 今日路線的商機（`today_route`）：促銷的列寫「想進Premium眼藥水(小口) × 1 口，報價草稿還沒成交」。
  判斷有沒有成交照舊看這家之後有沒有進過那個 sku。

## 出錯時

| 情況 | 結果 |
|---|---|
| 選的口不在今天進行中的那一期 | 422「促銷已經換期，請重新整理」 |
| 有填折扣，但整張都是促銷的口 | 422；畫面上按鈕先擋住 |
| 同一口列兩次、同一個品項不走促銷列兩次 | 422 |
| 一列同時給了 `sku/qty` 與 `promo_code/packs`，或兩種都沒給 | 422 |
| SAP 停機；要簽核時 OA 停機 | 跟現在一樣 503，報價不會開 |
| AI 抽出的口不是這一期的、或跟品項對不上 | 清掉品項與口，確認頁標「缺少品項」 |
| 確認頁存的口不存在、或跟品項對不上 | 422 |

## 測試

- 後端 `test_quotes.py`：
  - 一口的金額照每口售價 × 口數；除不盡的口（骨營粉劑）金額對得回每口售價。
  - 折扣只套在沒促銷的列；簽核 payload 的 `amount`、`cost` 只算那幾列，`total_amount` 是整張。
  - 「出錯時」表格裡報價那幾種。
  - `quote-promotion`：沒有進行中的一期回 null；常進品項裡有的品項 `usual` 是 true；別人的客戶回 404。
- 後端拜訪：
  - 提示裡有這一期的口；`promo_code` 對不上時被清掉。
  - 存欄位時 `promo_code` 的檢查。
  - 有口的意向回寫 SAP，四個新欄位寫得對；重送不重複。
- 後端讀報價：待處理事項與今日路線的寫法、金額。
- 前端：報價頁的合計（打折的部分加上口的金額）、擋住的原因；確認頁一行摘要。
- 真的 Gemini：用 `LLMFieldExtractor` 對文字逐字稿實跑上面表格的四句，再加兩句有口也有不走促銷的品項，
  確認輸出格式沒被拒絕（10/2 曾經整份 schema 被拒）、抽出來的口與口數對。
- 跑起整個系統，用 headless Chrome 開一張「Premium 小口 × 1＋人工淚液 20 瓶、折扣 2%」的報價，
  確認待處理事項的寫法與金額。

## 這次不做

- 滿額贈、禮券、組合加碼的計算（只顯示 PM 提醒原文）。
- 加贈的其他品項拆成報價的列。
- 報價轉成訂單、寫進交易資料。
- 提示「照供貨價比較便宜」。
- 談判卡、問答改成會開口的報價。
