# 方法卡

2026-09-30 ｜ 會議意見 7「經理教育員工的方法卡還是要留存給新人」｜總覽見 `2026-09-30-meeting-gaps-overview.md`

主管把「遇到這種情況怎麼談」寫成一張一張的卡，全公司的業務都看得到；業務用過之後按「有幫上／沒幫上」，
卡片累計採用次數。提案原型的「方法論知識庫」（提出者、採用次數）在正式系統裡的第一版。

## 為什麼做

- 交接交得出客戶名單，判斷與談法交不出來，新人只能重新摸索（提案時講的成因）。
- 主管現在教業務靠口頭與頻道裡的對話，人一調走就沒了，別區也學不到。

## 已定案的決定

1. **主管寫，全公司看**：主管與 IT 可以新增、修改、下架；所有登入的人都看得到，不分區、不分組。
2. **業務只回饋，不投稿**。按「有幫上／沒幫上」，採用次數＝有幫上的次數。
3. **內容是人寫的**，AI 不生成、不改寫、不摘要。
4. **卡片掛「情況」標籤**，跟談判卡判斷客戶狀況的訊號同一組，之後談判卡與新人頁靠標籤帶出相關的卡。

## 資料模型

`method_card`

| 欄位 | 說明 |
|---|---|
| `id` | 流水號 |
| `title` | 標題，2～40 字 |
| `situation` | 什麼時候用，最多 200 字 |
| `approach` | 怎麼做、怎麼說，最多 2,000 字 |
| `customer_type` | `chain`／`independent`／`clinic`，NULL 代表都適用 |
| `tags` | `list[str]`，至少一個，值只能是下面那組 |
| `author_id` | 寫的主管（FK `app_user`） |
| `status` | `published`／`retired` |
| `created_at`、`updated_at` | |

標籤（`METHOD_TAGS`，放 `models.py`；畫面上的名稱放前端）：

| 標籤 | 畫面上 |
|---|---|
| `competitor` | 客戶提到競品 |
| `interval_up` | 進貨間隔拉長 |
| `contract_ending` | 合約快到期 |
| `ar_overdue` | 帳款拖太久 |
| `festival` | 節慶檔期 |
| `cost` | 談進價與成本 |
| `newcomer` | 新人必看 |

`method_card_feedback`

| 欄位 | 說明 |
|---|---|
| `id` | 流水號 |
| `card_id` | FK `method_card`，卡片刪除時一起刪 |
| `user_id` | 按的人。自建帳號記在自己名下，不記在代理的那位 |
| `customer_id` | 在哪一家客戶的談判卡上按的；從方法卡清單按的是 NULL |
| `helped` | 有幫上／沒幫上 |
| `created_at` | |

唯一限制 `(card_id, user_id, customer_id)`，NULL 也算相同（Postgres 16 的 `NULLS NOT DISTINCT`）：
同一個人在同一家客戶對同一張卡只有一筆，再按一次是改答案，不是多一筆。

## 權限

- `SHARING_LEVEL["method_card"] = ROOT`：登入就看得到所有上架的卡。
- 新增：主管與 IT（`ManagerUser`）。修改、下架、重新上架：作者本人，或 IT。業務一律 403。
- 下架的卡業務看不到（清單不列、單張 404），作者在主管端看得到、可以重新上架。
- 作者被停用或降成業務：卡片照舊上架，之後只有 IT 改得了。

## API

`/api/methods`，都要登入。

| 方法 | 路徑 | 內容 |
|---|---|---|
| GET | `/api/methods?tag=&customer_type=&q=` | 上架的卡。`tag` 比對標籤；`customer_type` 列出適用該類型的（含都適用的）；`q` 在標題、情況、做法裡做部分比對。排序：採用次數多的在前，同數看最近修改 |
| GET | `/api/methods/mine` | 主管端：自己寫的卡，含下架的；IT 看全部 |
| POST | `/api/methods` | 新增（主管、IT） |
| PATCH | `/api/methods/{id}` | 改內容、標籤、適用類型、`status` |
| POST | `/api/methods/{id}/feedback` | `{helped, customer_id?}`，回傳更新後的次數 |

每張卡回傳：`id`、`title`、`situation`、`approach`、`customer_type`、`tags`、`author_name`、`status`、
`adopted`（有幫上幾次）、`not_helped`（沒幫上幾次）、`my_feedback`（我在這個情境按過什麼，沒按過是 null）、`updated_at`。
`my_feedback` 的情境＝請求帶的 `customer_id`，沒帶就是清單上按的那一筆。

規則放 `backend/app/services/method_cards.py`，路由放 `backend/app/api/methods.py`。
回饋不另設用量上限：唯一限制已經讓一個帳號對一張卡在一家客戶只有一筆。

## 畫面

- **方法卡頁 `/methods`**（所有人）：上方搜尋框與標籤篩選（一排可橫向捲動的標籤），下面是卡片清單。
  每張卡先顯示標題、情況、適用類型、作者、「採用 N 次」；點開看做法，底下兩顆鈕「有幫上」「沒幫上」，
  按過的那顆保持選取，可以改。
- **入口**：首頁標頭「使用說明」旁多一顆「方法卡」。主管端與組織管理頁不另外加（主管端有自己的分頁）。
- **主管端多一個分頁「方法卡」**（`/manager?view=methods`）：列自己寫的卡（IT 看全部），每張附採用與沒幫上的次數；
  「新增方法卡」開表單（標題、情況、做法、適用類型、標籤）；每張可以修改、下架、重新上架。
- 卡片的顯示抽成共用元件 `frontend/src/components/method-card.tsx`，方法卡頁、之後的談判卡與新人頁都用它。

## 示範資料

`catalog.py` 新增 `METHOD_CARDS`：十張左右手寫的卡，作者是四位主管，延續既有的情境——御松田搶陳列位、
北區魚油下滑、慢箋成長帶學名藥比價表、帳款超過 60 天、連鎖續約、獨立藥局小口進貨、節慶檔期要提前 21 天申請、
新人第一次拜訪怎麼開場。每個標籤至少一張，`newcomer` 至少三張。

回饋用自己的亂數產生：每張卡給一個目標採用次數（幾張四十幾次、幾張十幾次、一兩張個位數），
分散在五位業務與他們各自的客戶上，另外配一到兩成「沒幫上」。`created_at` 從灌資料那一刻往前推。

## 錯誤處理

- 標籤不在那一組、`customer_type` 不認得、字數超過：422，訊息寫出是哪一欄。
- 對下架的卡按回饋：404。
- `customer_id` 不存在：404（客戶清單是全公司共享，不需要再檢查範圍）。

## 測試

- **權限**：業務新增 403；主管改別人寫的 403、改自己的成功；IT 改誰的都行；下架的卡業務看不到、作者看得到。
- **清單**：標籤、適用類型、關鍵字三種篩選；排序照採用次數。
- **回饋**：同一人同一家再按是改答案、次數不重複算；不同客戶各算一筆；自建帳號按的記在自己名下；`my_feedback` 跟著情境變。
- **灌資料**：每個標籤至少一張卡；卡片的作者都是主管；回饋的人都是業務。
- **前端**（vitest）：標籤與類型的篩選邏輯。

## 第二輪：方法卡接進談判卡與新人頁

四項都合併之後做（總覽的「四項之間的關係」）。

- `method_cards.related(session, user, tags, customer_type, limit)`：上架的卡裡，標籤跟 `tags` 有交集、
  而且適用這個客戶類型的，照採用次數取前幾張。
- **談判卡**：客戶的訊號直接當標籤（`competitor`、`interval_up`、`contract_ending`、`ar_overdue`），
  再加 `festival`；成本導向的卡再加 `cost`。回應多一個 `methods`（最多 2 張），畫面在內部文件切入點下面加一區
  「主管教的做法」，回饋帶這家客戶的 `customer_id`。
- **新人第一週頁**：帶 `newcomer` 標籤的前 3 張，加一個「看全部方法卡」的連結。
