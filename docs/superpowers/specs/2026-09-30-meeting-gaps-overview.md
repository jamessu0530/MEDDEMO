## 已定案的決定（9/30 James）

1. **簽核**：模型有把握就由系統直接核准並留紀錄，其餘才送人簽，簽核頁附上模型的估計。
2. **節慶**：另建節慶行事曆，卡片圍繞下一個節慶，並帶入當期促銷。
3. **方法卡**：主管寫，全公司看得到、不分區；業務按「有幫上／沒幫上」。

## 四項之間的關係

四項各自獨立，可以同時做。只有一處相依：談判卡與新人第一週頁要帶出相關的方法卡。
這一段不放在那兩項裡做，等四項都合併後另外做一步「方法卡接進談判卡與新人頁」
（寫在方法卡那份文件的最後一節），那兩項在第一輪完全不碰方法卡。

```
第一輪（同時）  方法卡 ─┐
               簽核   ─┤
               談判卡 ─┼─→ 依序合併到 meeting-gaps ─→ 第二輪：方法卡接進談判卡與新人頁
               新人頁 ─┘
```

四項都會動到同一批共用檔案，但都是各加各的一段：`backend/app/models.py`（新表加在檔尾）、
`backend/app/main.py`（多掛一個 router）、`data/seed/catalog.py` 與 `generate.py`（新資料加在最後）、
`data/seed/seed.py` 的 `TABLES`、`frontend/src/App.tsx`（多一條路由）、`README.md`（多一節）。
另外談判卡與簽核都會改 `backend/app/api/customers.py` 和 `frontend/src/pages/customer.tsx`，改的是不同段落。
合併順序：方法卡 → 簽核 → 談判卡 → 新人頁，衝突由負責合併的人逐一解。

## 共用的約定

- **既有的假資料一筆都不變**。新資料在 `generate()` 的最後產生，用自己的亂數（`random.Random(seed + n)`），
  不從既有的那一條抽：多抽一次，後面所有客戶、交易、拜訪都會跟著變，評測題庫的答案、今日路線的模型、
  十幾個測試都寫死在現在的資料上。做完要驗證：同一個 `as_of` 下，既有各表的產出跟 main 完全相同
  （`oa_expense_form` 既有的出差單除了新欄位的預設值以外也相同）。
- **今日路線不受影響**：路線的「商機」會看報價草稿，所以假資料不新增任何 `sap_quotation_draft`。
- **畫面上的內容不讓 AI 生成**（NFR-1）：數字來自資料庫，文字來自內部文件的原文、設定檔裡人寫的句子、
  主管寫的方法卡。
- **權限**一律走 `services/scope.py`，新的資料種類在 `SHARING_LEVEL` 加一列，不另外寫規則。
  自建與第三方登入的帳號照舊代理示範業務林昱辰。
- **不新增角色**。內部文件裡的業務處長、總經理在系統裡沒有帳號，這兩關由坐在根節點的 IT 帳號代簽。
- **兩個時鐘**：跟業務資料比的日期一律用系統日 `app_today()`（到職幾天、下一個節慶、合約剩幾天）；
  `created_at` 這類紀錄時間照舊用真實時間。
- **資料表改了會自動重灌**：`models.py`、`catalog.py`、`generate.py` 一改，`schema_version` 的指紋就變，
  部署時 VM 上的資料庫會重建。指紋的檔案清單不變。
- **畫面**以手機為主，`max-w-md`，用既有的元件（`PageHeader`、`Notice`、`Button`、`Badge`…）與寫法。
- **測試**：後端 pytest、前端 vitest，沿用既有的測試資料庫與離線假模型。
- **README** 每項各加一節，寫法照現有的章節：做了什麼、為什麼這樣定、哪裡沒做。

## 平行開發時的環境

- 每個人在自己的 worktree（`.worktrees/<分支>`）與分支上做，從 `meeting-gaps` 開出去。
- 測試各用自己的資料庫與 Redis：`TEST_DB_NAME=meddemo_test_<代號>`、`TEST_REDIS_URL=redis://127.0.0.1:6379/<11～14>`。
  預設的 `meddemo_test` 與第 15 號庫留給主要的工作目錄。
- **不可以對開發用的資料庫跑 `data/seed/seed.py`**（會清掉整個資料庫）。要一份灌好的資料（例如訓練模型），
  另建一個資料庫，用 `--database-url` 指過去。
- 不推送、不合併到 main：推 main 會觸發部署。
