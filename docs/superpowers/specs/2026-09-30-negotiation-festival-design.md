# 談判卡改版：依節慶，連鎖看顧客、獨立店看成本

2026-09-30 ｜ 會議意見 5「談判卡都要改，專注的東西根據 festival 去設計（連鎖：顧客導向，獨立店家：成本導向）」｜
總覽見 `2026-09-30-meeting-gaps-overview.md`

現在只有連鎖客戶有談判卡，內容是「我方品項進貨次數對照同區平均、毛利結構、內部文件的切入點」，跟什麼時候去談無關。
改成每一家都有卡，卡片圍繞下一個節慶：連鎖談「顧客要買的時候你架上有沒有」，獨立藥局與診所談「這一檔進貨成本多少、賣一個賺多少」。

## 已定案的決定

1. **每種客戶都有談判卡**。連鎖是顧客導向；獨立藥局與診所是成本導向（會議只講到獨立店家，診所一樣是單店、自己算成本，歸同一邊）。
2. **卡片圍繞下一個節慶**：節慶行事曆另外建，成本導向那一邊帶入當期促銷。
3. **節慶行事曆放設定檔** `backend/app/resources/festivals.json`，不進資料庫：跟 `negotiation_topics.json` 同一個道理，
   改檔就能調整（NFR-10），也不必為了加一個節慶重灌資料。
4. **不讓 AI 生成**：數字來自資料庫，節慶那一句話是設定檔裡人寫的，切入點是內部文件的原文。
5. **不做「去年同期成長」**：假資料的交易沒有節慶的季節性，算出來只會是雜訊。顧客導向改看得到的事實：
   節慶主推的品類裡，這家架上有什麼、缺什麼。

## 節慶行事曆

`festivals.json`，一個節慶一年一筆：

| 欄位 | 說明 |
|---|---|
| `id` | 例如 `2026-double11` |
| `name` | 雙 11、過年、母親節、端午、父親節、中秋 |
| `date` | 節日當天 |
| `lead_days` | 通路提前幾天開賣，預設 28 |
| `categories` | 主推品類，值是品項表的類別（保健品、一般用藥、醫材、慢性處方） |
| `customer_note` | 顧客導向的一句話：這個節慶誰在買、買什麼 |
| `cost_note` | 成本導向的一句話：這一檔進貨要注意什麼 |

內容從 2026 年過年寫到 2027 年雙 11（2026：過年 2/17、母親節 5/10、端午 6/19、父親節 8/8、中秋 9/25、雙 11 11/11；
2027：過年 2/6、母親節 5/9、端午 6/9、父親節 8/8、中秋 9/15、雙 11 11/11）。

**下一個節慶**＝節日在系統日當天或之後、最近的那一個。決賽日 2026-10-28 看到的是雙 11（還有 14 天）。
行事曆裡沒有之後的節慶時，卡片不顯示節慶區塊，其餘照常；一個測試確認行事曆涵蓋決賽日之後至少 12 個月。

## 卡片內容

### 共用：節慶區塊（最上面）

節慶名稱、日期、還有幾天、主推品類，下面一句話：連鎖用 `customer_note`，其他用 `cost_note`。

### 連鎖：顧客導向

1. **檔期**（照《檔期活動申請與成效回報》）：
   - 申請期限＝節日 − `lead_days` − 21 天（文件規定活動開始前 21 天要送申請）。
   - 下一個節慶的期限已經過了，就照實寫「雙 11 的檔期來不及申請了」，改列下一個還來得及的節慶與它的期限
     （決賽日會是過年，最晚 2026-12-19 送申請）。
   - 檔期費用上限＝這家前 3 個月平均月進貨金額的 15%（文件的規定），直接算出金額。
2. **架上有什麼**：主推品類裡，這家近半年進貨金額最高的四個我方品項，近 90 天每月進貨幾次、對照同區同類型客戶的平均，
   低於平均標紅（現有的算法，多一個品類條件）。主推品類裡這家一項都沒進，就退回不分品類並註明。
3. **架上缺什麼**：主推品類裡，同區其他連鎖客戶近 90 天超過一半有進、這家近 180 天沒進過的品項，
   最多三個，寫「同區 38 家連鎖裡 25 家有進」。沒有就不顯示這一區。
4. **我方底線**：現有的毛利結構（上架費、通路獎勵、淨毛利率對照同區平均），內容不變，只改標題。

### 獨立藥局與診所：成本導向

1. **這一檔的進價**：進行中那一期促銷裡屬於主推品類的品項，一個品項一列，取搭贈後每個最便宜的那一口：
   搭贈說明、每口售價、搭贈後每個多少、建議售價、照建議售價賣一個賺多少與毛利率，另外標出這個品項最小一口要多少錢
   （獨立店在意一次要壓多少貨）。照毛利率由高到低，最多五個。
   - 數字讀語意層的 `v_promotion_item`（每個平均價、折數），跟促銷頁、問答查到的一樣，不另外算一套。
   - 主推品類裡沒有促銷品項就改列全部品類並註明；沒有進行中的促銷就寫「這一期沒有促銷」。
2. **這家的條件**：
   - 供貨價是建議售價的幾成（`pricing.SUPPLY_PRICE_FACTOR`：獨立藥局 95%、診所 100%）。
   - 通路獎勵（《連鎖通路合約條件》：獨立藥局 2%，診所不適用）。
   - 付款條件月結 30 天，目前最久一筆帳款幾天。
   - 業務可以直接給的折扣 3%，超過要簽核（《報價權限》）。
   - 近 90 天進貨金額與單次平均金額。
   文件裡的數字寫成常數並註明出處，寫法照 `customer_profile.py` 現有的 `AR_WATCH_DAYS`。

### 共用：內部文件的切入點

照舊最多三段原文。`negotiation_topics.json` 多兩組，排在最前面：

- `festival`（連鎖而且有下一個節慶）：找《檔期活動》的申請期限與費用上限。
- `cost`（獨立藥局與診所）：找《報價權限》業務的折扣權限、《連鎖通路合約條件》獨立藥局與診所的通路費用。

關鍵字由實作時對著文件調，調到「每一組都找到想要的段落」那個測試通過為止。原本五組不變。

## API

`GET /api/customers/{id}/negotiation`：拿掉「只有連鎖客戶」的 409，權限不變（`customer_profile`）。回應：

| 欄位 | 連鎖 | 獨立藥局、診所 |
|---|---|---|
| `orientation` | `customer` | `cost` |
| `festival` | 名稱、日期、還有幾天、主推品類、那一句話；沒有下一個節慶是 null | 同左 |
| `campaign` | 來得及申請的那個節慶、期限、還有幾天、費用上限、`missed`（期限已過的節慶名稱） | null |
| `shelf` | 品項清單（現在的 `turnover` 改名）與 `scoped`（是不是限定在主推品類） | null |
| `gaps` | 缺的品項：料號、名稱、同區幾家裡幾家有進 | null |
| `margin` | 照舊 | null |
| `deals` | null | 促銷品項清單與 `scoped` |
| `terms` | null | 上面那幾項條件 |
| `tips` | 照舊 | 照舊 |

程式留在 `backend/app/services/customer_profile.py` 會太長（現在 408 行）：談判卡的部分搬到新檔
`backend/app/services/negotiation.py`，節慶行事曆的讀取與「下一個節慶」放 `backend/app/services/festivals.py`，
`customer_profile.py` 只留客戶檔案。

## 畫面

- **客戶檔案頁**：「談判卡」按鈕每種客戶都有。
- **談判卡頁**：最上面節慶區塊；下面依 `orientation` 顯示上面列的各區；最下面兩顆鈕照舊（客戶檔案、開始拜訪）。
  頁面標題下的副標寫「顧客導向」或「成本導向」。
- **首次使用引導**：第一步的說明把「連鎖客戶另有談判卡」改成每一家都有依節慶準備的談判卡。

## 錯誤處理

- `festivals.json` 讀不到或格式不對：當成沒有節慶，卡片其餘照常，log 記一筆。
- 這家近半年沒有進貨：架上那一區寫「近半年沒有進貨紀錄」（照舊）。
- 看不到的客戶照舊 404。

## 測試

- **節慶**：系統日在節日前、當天、隔天各挑到哪一個；行事曆的日期由早到晚、品類都是品項表裡有的、涵蓋決賽日後 12 個月。
- **檔期**：決賽日雙 11 的期限已過、改列過年與 12/19；費用上限等於前 3 個月平均月進貨的 15%。
- **架上**：限定在主推品類；主推品類沒有品項時退回全部並標明。
- **缺口**：只列同區連鎖過半有進、這家半年沒進的；不超過三個。
- **成本導向**：獨立藥局與診所都拿到卡（原本的 409 測試改掉）；促銷品項只來自進行中那一期、一個品項一列、
  數字跟 `v_promotion_item` 一樣；條件依客戶類型不同。
- **切入點**：七組各自找到想要的段落。
- **前端**：型別檢查與 lint 通過；畫面上算的東西（例如毛利率的格式）有就加 vitest。

## 不在這次範圍

- 檔期成效（檔期營收、檔後回落）：資料庫沒有這份資料。
- 去年同期的節慶成長。
- 檔期申請單（OA）。
- 依節慶自動排進今日路線。
- 帶出相關的方法卡：四項都合併後另外做（見方法卡的設計文件）。
