# 在頻道裡 @熊熊滾 回答

2026-10-01

在頻道（群組）裡 @熊熊滾，它就讀這個頻道最近的對話回答；要查公司文件的題目，跟問答頁的「知識」走同一條 CRAG。
這是把〈頻道與 AI 主理記憶〉（2026-09-28）第 3 階段的「被 @ 時回答」提前、單獨做：
〈附件〉（2026-10-01）把它排在第 5 階段，前面還有附件三個階段與記憶，要等很久。
這次只做 @ 回答，記憶看板、週摘要、逾期提醒、風險通報進頻道照原本的順序之後再做。

## 跟原設計不一樣的地方

| | 原設計（2026-09-28） | 這次 |
|---|---|---|
| 給模型的內容 | 看板 ＋ 最近 50 則 ＋ 客戶基本資料 | 最近 50 則 ＋ 客戶基本資料（還沒有看板；記憶做完再接上） |
| 公司文件 | 不查 | 跟問答頁同一條 CRAG：先查內部文件，找不到依據才上網，用藥題與公司內部題不上網 |
| 怎麼叫 | `@AI` | `@熊熊滾`、`@熊熊`、`@AI` |
| 用量 | 沒寫 | 一次 @ 算一次「提問」，跟問答頁共用額度 |

不查銷售數字、不讀拜訪紀錄，理由跟原設計一樣：頻道裡的回答所有成員都看得到，現有的權限是依個人算的。
內部文件沒有分權限（`document_chunk` 全公司都查得到），放進頻道不會讓資料傳到不該看到的人手上。

## 怎麼叫熊熊滾

- 訊息裡有 `@熊熊滾`、`@熊熊` 或 `@AI`（英文不分大小寫；中文輸入法打出來的全形 `＠`、`ＡＩ` 也算）就算叫它。
  `@` 前面不能緊接英文字母、數字或 email 用的符號（`x@ai.com` 不算），接中文可以（`請@熊熊滾回答`，中文打字常常不空格）；
  `@AI` 後面不能緊接英文字母或數字（`@AIDS` 不算），接中文可以（`@AI請問`）。
- 判斷在寫入時做，結果存在訊息的 `mentions_ai`。之後改了判斷規則，舊訊息不會被重新解讀。
- 熊熊滾自己的訊息（`kind = ai`）不判斷，不會自己叫自己。

## 熊熊滾怎麼回答

新的背景工作 `app.services.channel_ai.answer(message_id)`，排在新的 `channels` 佇列。

1. 讀提問那一則、它所在的頻道（`describe`），以及這個頻道**編號不大於提問那一則**的最近 50 則訊息（含提問本身）。
   提問之後才進來的訊息不給，免得答非所問。頻道已經封存就直接結束，不回。
2. 客戶討論串另外給客戶基本資料：名稱、類型、連鎖體系、縣市、地點、等級、負責人。
   都是 `customer_basic`（全公司看得到）的欄位；合約到期日不給。
3. **第一次呼叫模型：判斷題目**（`LLM.json`，推理強度 low）。回傳：
   ```json
   {"route": "documents" | "chat", "question": "…", "answer": "…"}
   ```
   - `documents`：公司規定、產品、作業流程、退貨、報價權限、陳列這類要查文件的題目。
     `question` 是參考前面的對話、改寫成單獨看得懂的一句問題，**不放同事的名字**（這句可能被拿去上網搜尋）；`answer` 留空。
   - `chat`：只看對話與客戶基本資料就答得出來的（「剛剛大家說了什麼」「這家客戶誰負責」）、打招呼、閒聊。
     `answer` 直接是回答；`question` 留空。
   - 提示裡寫明：跟公司規定、產品、流程有關的一律走 `documents`，不能憑對話或常識自己回答；
     對話裡也查不到的事就說不知道，不要猜。
   - 輸出驗證不過（`documents` 卻沒有 `question`、`chat` 卻沒有 `answer`）當作失敗。
4. `documents` 走 `knowledge.answer_knowledge(session, llm, question, on_step, embed_query)`，跟問答頁同一個入口：
   - `answered`：答案後面空一行接出處，一個來源一行。內部文件寫「[1] 文件標題｜小節」，網頁寫「[2] 標題 網址」。
   - `no_evidence`：直接用它的文案（內部文件找不到、用藥題請問醫師或藥師、公司內部題請問主管、網路上也找不到）。
   - `failed`：用它的 `error_message`（逾時、網路搜尋出錯）。
   - `on_step` 不記：問答頁的查詢過程（`query_trace`）掛在 `ask_record` 上，頻道沒有對應的地方，也沒有畫面要看。
5. 回答寫成 `kind = ai`、`author_id` NULL、`reply_to_id` 指向提問那一則。

### 失敗

下面幾種情況都發一則固定的「我暫時答不出來，請稍後再 @ 我一次。」，一樣 `reply_to_id` 指向提問：

- AI 模型沒設定（`NotConfigured`）、模型出錯、第一次呼叫的輸出不能用；
- `answer_knowledge` 丟出例外；
- 發言時背景工作排不進去（Redis 連不上）：在發言的 API 裡直接發道歉，提問那一則照樣留著。

背景工作本身不重試，提問的人可以再 @ 一次。

工作超過 RQ 的上限（預設 180 秒）被砍掉時來不及發道歉；CRAG 自己 45 秒就逾時，正常不會走到這裡。
真的發生時，畫面三分鐘後停止顯示「熊熊滾正在想」，提問的人看得出來沒有回覆。

## 寫入與訊息順序

- `channel_message` 加兩欄：
  - `mentions_ai`（bool，預設 false）
  - `reply_to_id`（FK `channel_message.id`，`ondelete="SET NULL"`）：熊熊滾回答的是哪一則
- 〈頻道設計〉第一階段留下的待辦「訊息編號的順序」這次一起做：所有寫訊息的地方走同一個函式，
  寫之前先 `SELECT … FROM channel WHERE id = … FOR UPDATE`。同一個頻道的寫入排隊進行，編號順序等於寫入完成的順序，
  輪詢「這則之後的新訊息」就不會漏掉熊熊滾在背景寫的回答。
- `models.py` 會改，`schema_version` 的指紋跟著變，部署時照現有機制自動重建資料庫（展示環境裡使用者發過的訊息會清掉）。

## 用量上限

- 一次 @熊熊滾 算一次「提問」（`usage.LIMITS["ask"]`：每個帳號每小時 50 次、全系統每天 200 次），跟問答頁共用。
  走的是同一條 CRAG，花費差不多。
- 用量 middleware 只看網址，分不出訊息有沒有 @，所以在發言 API 裡另外扣：訊息寫入之後、commit 之前扣一次「提問」，
  超過上限就 rollback、回 429（文案跟問答頁一樣），訊息不會留下。發言本身的「頻道發言」額度照舊由 middleware 扣，
  回 429 時 middleware 會把它還回去。
- Redis 連不上時放行，跟 middleware 一樣。

## API

- `MessageItem` 多 `mentions_ai`、`reply_to_id`。
- `POST /api/channels/{id}/messages`：有 @ 的訊息 commit 之後排 `channel_ai.answer`；超過「提問」上限回 429。

## 測試

沿用 pytest 的測試資料庫與照劇本回應的假模型（`tests/test_asks.py` 的 `ScriptedLLM` 做法）；CRAG 本身已有測試，這裡把 `answer_knowledge` 換掉，只測頻道這一層怎麼用它。

- **判斷 @**：三種寫法、全形半形、大小寫都觸發；`x@ai.com`、`@AIDS`、沒有 @ 的「熊熊滾」不觸發。
- **排工作**：有 @ 的訊息排進 `channels` 佇列、`mentions_ai` 為 true；沒有 @ 的不排。
- **chat**：模型回 `chat` 時直接發它的 `answer`，`reply_to_id` 正確，不呼叫 `answer_knowledge`。
- **documents**：把模型改寫的 `question` 交給 `answer_knowledge`；`answered` 附出處（文件與網頁兩種格式）；
  `no_evidence` 與 `failed` 用它的文案。
- **給模型的內容**：只有這個頻道、編號不大於提問的訊息；客戶討論串有客戶基本資料、沒有合約到期日；
  不含別的頻道的訊息。
- **失敗**：模型沒設定、模型丟例外、輸出缺欄位、`answer_knowledge` 丟例外、排工作失敗，都發道歉訊息。
- **封存**：頻道在排隊期間被封存就不回。
- **用量**：有 @ 的發言扣一次「提問」、沒有 @ 的不扣；超過上限回 429，訊息沒寫進去，「提問」的計數也不會因為這次被擋而增加。
- **訊息順序**：兩條連線同時在同一個頻道寫訊息，後拿到鎖的那一則編號比較大。
- **前端**（vitest）：「熊熊滾正在想」的判斷：三分鐘內沒回覆才顯示、有回覆或超過三分鐘就不顯示。
