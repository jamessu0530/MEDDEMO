# 優惠與合約簽核

2026-09-30 ｜ 會議意見 9「監督式學習：簽核不一定要給主管 1.優惠 2.合約」｜總覽見 `2026-09-30-meeting-gaps-overview.md`

業務給客戶折扣、幫連鎖客戶續約，現在系統裡沒有簽核。這次加兩種申請單，跟出差單共用同一套 OA；
誰要簽照內部文件的規則定，其中「規則上主管就能簽」的單，模型很有把握會過就由系統直接核准。

## 為什麼做

- 報價現在直接開草稿，不看折扣權限；《報價權限》寫的 3%／8%／12% 三級在系統裡沒有作用。
- 每一張都等主管簽，主管的簽核匣塞滿「一看就會過」的單，業務在客戶面前等不到答案。
- 過去的簽核結果就是現成的標籤：哪種單會過、哪種會被退，可以學。

## 已定案的決定

1. **兩種新申請單**：優惠（報價折扣）、合約（連鎖續約與費率）。跟出差單共用申請匣、簽核匣、流程、意見、活動日誌。
2. **規則決定最高簽到哪一級，模型決定主管這一級能不能免**。超過主管權限的單一律送人，模型不碰。
3. **簽核不一定要給主管的三種情況**：3% 以內的折扣是業務自己的權限，不開單；主管級的單模型有把握就系統核准；
   超過主管權限的逐級往上送處長、總經理。
4. **模型跟今日路線同一套**：logistic regression、純 Python、權重存成 JSON 進 git、用指令重新訓練。
5. **特徵在送單當下算好存在單上**，之後不回頭改。訓練只讀單上的特徵與簽核結果，人簽過的新單自動變成下一次訓練的資料。
6. **業務處長、總經理沒有帳號**，這兩關指派給根節點的 IT 帳號（IT 本來就能代簽），關卡名稱照內部文件寫。

## 規則：誰要簽

照《報價權限與折扣審核》《連鎖通路合約條件》。

| 申請 | 條件 | 關卡（依序） |
|---|---|---|
| 優惠 | 折扣 ≤ 3% | 不用簽，直接開報價 |
| 優惠 | 3% < 折扣 ≤ 8% | 區處主管 |
| 優惠 | 8% < 折扣 ≤ 12% | 區處主管 → 業務處長 |
| 優惠 | 12% < 折扣 ≤ 20% | 區處主管 → 業務處長 → 總經理 |
| 合約 | 照原費率續約 | 區處主管 |
| 合約 | 上架費率或通路獎勵比率有任何調整 | 區處主管 → 業務處長 |

- 折扣是整張報價一個百分比，0～20%、每 0.5% 一格，套在標準供貨價上。超過 20% 不收（422）。
- 區處主管＝申請人的直屬主管（跟出差單一樣）；處長、總經理＝根節點的 IT 帳號。
- 「照原費率續約由區處主管核准」內部文件原本沒寫，在 `data/documents/05-上架費與通路獎勵.md` 的
  〈連鎖合約的續約與費率調整〉補一句，並重跑知識題評測相關的測試。
- 搭贈換算成折扣、檔期費用不在這次範圍。

## 模型：主管這一級能不能免

### 什麼時候由系統核准

四個條件都成立才由系統核准，否則照規則送人：

1. 規則上最高只到區處主管。
2. 模型檔存在，而且那一種申請有訂出門檻（見下面「訓練」）。
3. 模型估計的核准機率 ≥ 門檻。
4. 這家客戶沒有超過 60 天的帳款（跟客戶檔案同一個門檻 `AR_WATCH_DAYS`）。這一條不交給模型：帳款出問題的客戶再給優惠，應該有人看過。

系統核准的單：第二關記成「系統核准」（沒有簽核人），狀態直接是已核准，活動日誌寫
「模型估計核准機率 94%，高於門檻 90%，系統核准」，效果立刻生效（見「核准之後」）。

送人簽的單一樣記下機率，簽核頁顯示給主管參考。

### 特徵

| 優惠 | 說明 |
|---|---|
| `discount_pct` | 折扣百分比 |
| `margin_after` | 折後毛利率＝（折後金額－成本）÷ 折後金額 |
| `log_amount` | 這張報價折後金額的對數 |
| `log_sales_90d` | 客戶近 90 天進貨金額的對數 |
| `ar_age_days` | 最久一筆未收帳款幾天 |
| `competitor_recent` | 近 90 天已確認的拜訪有沒有提到競品 |
| `grade_weight` | 客戶等級（A 3、B 2、C 1） |

| 合約 | 說明 |
|---|---|
| `fee_change` | 上架費率＋通路獎勵比率合計變動幾個百分點（往上調是正的） |
| `term_years` | 續約幾年 |
| `net_margin` | 近 90 天淨毛利率（扣掉上架費與通路獎勵） |
| `log_sales_90d` | 客戶近 90 天進貨金額的對數 |
| `interval_change` | 進貨間隔的變化（跟今日路線同一個算法） |
| `ar_age_days` | 最久一筆未收帳款幾天 |
| `grade_weight` | 客戶等級 |

客戶狀態的算法盡量重用 `route_model.candidates` 與 `customer_profile`，時間窗與門檻跟那兩處一致。

### 簽核頁上的理由

不用模型的特徵貢獻寫理由（今日路線已經說明過：貢獻值受標準化影響，會跟真正的原因對不上）。
照門檻列事實：折扣幾 %、主管權限到幾 %；折後毛利率幾 %；帳款最久幾天（超過 60 天標紅）；
近 90 天有沒有提到競品；合約則列費率變動與淨毛利率。

### 訓練

- `backend/scripts/train_approval_model.py`：讀已經有結果的優惠與合約申請單，特徵用單上存的那份，
  標籤是核准（1）或駁回、退回（0）。系統核准的單不算進去（那是模型自己的判斷，不是人的）。
- 兩種申請各一個模型，存在 `backend/app/resources/approval_model.json`：`{"discount": {...}, "contract": {...}}`，
  每個有 `mean`、`sd`、`weights`、`bias`、`threshold`、成績。
- 照時間切，最後四分之一當測試期。門檻從 0.80、0.85、0.90、0.95 裡挑最低、測試期上「模型說會過的真的有過」
  至少 95%、而且至少有 20 張的那一個；都達不到就是 `null`，那一種申請不做系統核准。
- 成績（AUC、門檻、門檻上的命中率、主管級申請有幾成會被系統核准）印出來並寫進 README。
- logistic regression 的 `fit` 與 `auc` 從 `train_route_model.py` 搬到 `backend/app/services/logreg.py`，兩支訓練程式共用；
  今日路線的權重檔不能因此改變。
- 模型檔不在：所有單都照規則送人（跟今日路線沒有模型時改用規則一樣）。
- **不自動重新訓練**：人簽過的新單已經在收，要更新模型就重跑指令。決賽被問到照實說。

## 資料模型

### `oa_expense_form`：從出差單變成三種申請單

表名不改（改了要動灌資料的 SQL 與一整排程式），docstring 改成「模擬 OA 申請單」。

| 欄位 | 變動 |
|---|---|
| `kind` | 新增：`trip`／`discount`／`contract`，預設 `trip` |
| `visit_id`、`trip_date` | 改成可以是 NULL；出差單一定有，其他兩種一定沒有 |
| `request_date` | 新增：送單當下的系統日（`app_today()`）。出差單是 NULL |
| `payload` | 新增 JSONB：申請內容（下面） |
| `required_level` | 新增：`manager`／`director`／`gm`，規則算出來的最高關卡；出差單是 `manager` |
| `model_probability` | 新增：送單當下模型估計的核准機率，沒有模型是 NULL |
| `model_features` | 新增 JSONB：送單當下的特徵 |
| `auto_approved` | 新增：是不是系統核准的，預設 false |

一條 CHECK 約束規定：`trip` 有 `visit_id` 與 `trip_date`、沒有 `payload`；另外兩種相反，而且有 `request_date`。

`payload`：

- 優惠：`quote_no`（假資料的歷史單是 null）、`discount_pct`、`list_amount`（折前）、`amount`（折後）、`cost`、`reason`。
- 合約：`term_months`（12 或 24）、`listing_fee_rate`｛`from`、`to`｝、`channel_reward_rate`｛`from`、`to`｝、
  `old_end_date`、`new_end_date`、`reason`。

單號：出差單照舊 `OA` 開頭；優惠 `DC`、合約 `CT`，後面一樣是年月加五碼流水號，各自編號。

### 其他表

- `oa_approval_step.user_id`、`oa_activity.actor_id` 改成可以是 NULL，NULL 代表系統；
  畫面上顯示「系統（模型）」。`OA_ACTIVITY_ACTIONS` 多一個 `auto_approved`。
- `sap_quotation_draft` 多 `discount_pct`（預設 0），`unit_price` 存折扣後的單價。
  `status` 加 CHECK：`draft`（可以送給客戶）、`pending_approval`（等簽核）、`rejected`（被駁回或退回）。

## 流程

### 優惠：在報價頁填折扣

1. 報價頁多一個「折扣」欄與「理由」欄（超過 3% 必填，最多 500 字）。
   欄位下面即時寫出這個折扣要誰簽：「在你的權限內，直接送出」「要區處主管核准，系統有把握會直接核准」
   「要區處主管與業務處長核准」…，以及折扣後的金額。
2. 送出：
   - ≤ 3%：照現在的流程開報價草稿，不開單。
   - > 3%：報價寫成 `pending_approval`，同一個交易裡開優惠申請單、算特徵與機率、照上面的條件決定系統核准或送人。
3. 回到客戶檔案頁的提示：「報價 Q… 已開，折扣 5% 系統已核准（過去類似的申請 94% 會過）」
   或「…折扣 7% 已送陳建宏簽核」。
4. 客戶檔案的待處理事項：等簽核的報價標「待簽核」，被駁回的不列。

### 合約：在客戶檔案頁申請續約

1. 連鎖客戶的客戶檔案頁多一列合約到期日與「申請續約」；合約 3 個月內到期時這一列標出來。
2. 續約頁 `/customers/:id/contract`：顯示目前條件（到期日、上架費率、通路獎勵比率——系統沒有合約表，
   費率用近 90 天交易的加總相除算出來，跟談判卡的毛利結構同一個算法），填續約 12 或 24 個月、新的兩個費率
   （預設是原值）、理由。費率一改，頁面上就寫「費率有調整，要送業務處長」。
3. 同一家客戶同時只能有一張還沒簽完的合約申請（409）。

### 簽核

- 關卡照規則一次建好：第一關請求者（已完成）、第二關等簽、後面的關卡是 `waiting`。
- 核准一關：那一關完成，下一關變成等簽；沒有下一關了，整張單才是已核准。駁回或退回：整張單結束。
  出差單只有一關，行為跟現在一樣。
- 主管的簽核匣列三種單，各有種類標籤與一句摘要（「折扣 6%，報價 NT$ 48,200」「續約 12 個月，費率不變」）；
  優惠與合約多一行「模型估計核准機率 62%」與理由。
- 簽核匣下面多一區「系統已核准」：自己底下的人最近 30 張由系統核准的單，給主管事後查。IT 看全公司。
- 單張申請單頁依種類顯示內容；流程分頁看得到「系統核准」那一關。

### 核准之後

| 申請 | 核准 | 駁回或退回 |
|---|---|---|
| 優惠 | 報價從 `pending_approval` 變 `draft` | 報價變 `rejected` |
| 合約 | 客戶的合約到期日改成新的到期日（原到期日與系統日取晚的，再加續約月數） | 不變 |

新費率只記在申請單上：系統沒有合約表，交易的費率是假資料產生時定的，不回頭改。

## 示範資料

`generate.py` 用自己的亂數產生一年的歷史申請單，全部已經有結果：

- 優惠約 900 張：大多落在 3%～8%，少數到 12%，很少超過 12%。合約約 300 張，三分之二照原費率。
- 簽核結果照特徵決定，再加雜訊：折扣越深、折後毛利越低、帳款拖越久越容易被退；有競品壓力、進貨量大、
  等級高比較會過。合約則是費率調得越多越難過，淨毛利低、帳款久也難過。沒有這層關聯，模型學不到東西
  （今日路線當初就是這樣，AUC 0.51）。
- 特徵在產生器裡照同一組定義算好，寫進 `model_features`；一個測試抽幾張比對產生器算的跟執行時算的一樣，
  免得兩邊各改各的。
- 歷史的優惠申請單**不建報價草稿**（`quote_no` 是 null）：報價草稿會影響今日路線的商機。
- 每張單的兩關、活動日誌照既有出差單的做法在 `seed.py` 補。
- 另外留幾張還沒簽的給展示用：陳建宏的簽核匣有兩張優惠（一張 6%、一張 10% 要再送處長）與一張合約；
  林昱辰名下有兩張系統核准的。這幾張一樣沒有報價草稿。

## 錯誤處理

- 折扣不在 0～20 或不是 0.5 的倍數、超過 3% 沒寫理由：422。
- 模擬 SAP 停機：照現在回 503。模擬 OA 停機而這張要簽：503，報價也不開。
- 模型檔壞掉或少了某個特徵：當成沒有模型，送人簽，log 記一筆。
- 不是等你簽的單按簽核：403（照舊）。

## 測試

- **規則**：每一級折扣與兩種合約各自建出對的關卡；20% 以上 422；3% 以內不開單。
- **系統核准**：用假的模型檔——機率過門檻且沒有逾期帳款會系統核准、報價變 `draft`；機率不夠、帳款超過 60 天、
  規則要到處長、沒有模型檔、門檻是 null，都送人。
- **逐關**：主管核准後換處長等簽、報價還是 `pending_approval`；處長核准才生效；中途駁回報價變 `rejected`。
- **合約**：核准後到期日延長；同時第二張 409；不是連鎖 409。
- **權限**：別的業務看不到這張單；主管只看得到自己底下的；IT 都看得到也能代簽；自建帳號開的單記在代理的那位名下。
- **出差單不變**：既有的出差單測試全部照過。
- **訓練**：`logreg.fit` 在一小組人造資料上學得到方向；今日路線的權重檔重新訓練後不變；
  假資料的歷史單兩種結果都有、特徵齊全；產生器與執行時的特徵一致。
- **前端**（vitest）：折扣對應哪幾關的換算。

## 不在這次範圍

- 撤銷系統核准；主管調整門檻的畫面。
- 自動重新訓練。
- 業務處長、總經理的帳號與角色。
- 檔期申請單、搭贈換算折扣、信用額度與付款條件的例外申請。
- 合約費率寫回交易資料；合約表。
- 被退回的單修改後重送。
