# 組織管理與 IT 最高權限

2026-09-28

讓組織樹可以在系統裡改，並新增最高權限的「IT」角色：看得到、也動得了全公司的資料，並且是唯一能改組織的人。
接續〈組織樹權限模型〉（2026-09-24），那份文件把「沒有組織維護介面」列為不在範圍，這份補上。

## 為什麼改

- 組織寫死在 `data/seed/catalog.py`，改一個人的主管要改檔案、重灌整個資料庫。
- 主管端三個分頁各用一套規則：提問與風險通報看「轄區」、簽核找「該區工號最小的主管」、點進客戶檔案看「組織樹」。
  每區只有一位主管時看不出差別；9/27 北區多了 M04 之後，M04 的簽核匣永遠是空的、M01 的每則通報點進去都 404、
  兩位主管共用同一個已讀狀態。組織一旦能在畫面上改，這種不一致只會更多。

## 已定案的決定

1. **IT 看得到也動得了全部資料**，不是唯讀。
2. **M04 改成 IT**，工號改為 `A01`（`M` 開頭是主管，之後新主管照 `M04`、`M05` 編下去），信箱不變。
   林昱辰、王冠宇回到陳建宏 M01 底下，北區又只有一位主管。
3. **組織編輯支援四種操作**：換業務的直屬主管、把主管調到別區、改角色（業務↔主管）、新增／停用公司帳號。
4. **客戶移交兩種都做**：停用或升主管時整批轉給一位業務；客戶檔案頁給 IT 一個「換負責人」按鈕，單獨換一家。
5. **組織與帳號的異動留紀錄**，組織管理頁看得到。
6. **做法：IT 坐在根節點上**，路徑就是 `TW`。不走 `Scope.everything()`，也不在各個檢查點寫 `if role == "it"`。

## 資料模型

### 角色與位置

`role` 多一個 `it`。三種角色在樹上的位置是固定的：

| 角色 | 掛在哪 | 路徑 | 深度 |
|---|---|---|---|
| `it` | 根節點（`unit_id = TW`） | `TW`，就是根節點本身，不接自己的工號 | 1 |
| `manager` | 一個區（`unit_id = TW.N`） | `TW.N.M01` | 3 |
| `sales` | 一位主管底下（`manager_id`） | `TW.N.M01.U01` | 4 |
| 自建／第三方登入 | 不在樹上，代理 U01 | NULL | — |

`org_position` 約束改成依角色檢查形狀：業務一定有 `manager_id`、主管與 IT 一定有 `unit_id`、自建帳號三個都空且有
`acts_as_user_id`。約束查不到別的列，所以「主管只能掛在區、IT 只能掛在根、業務的主管一定是主管」由
`paths_from_reports` 檢查，它同時是灌資料與每次組織異動後的驗證點，違反就丟 `ValueError` 並點名是誰。

IT 的路徑只有一層，截到任何共享層級都還是 `TW`，於是全國的讀與寫都涵蓋。這跟「主管看得到屬下」是同一個式子的
結果：`Scope`、語意層的 `app_in_scope`、客戶與拜訪的 API 一行都不用改。

### `region` 改成衍生值

`app_user.region` 目前是灌資料時寫死的字串，組織一改就會跟樹對不上。改成 `rebuild_org_paths` 重算路徑時一起算：
在樹上的人取路徑前兩層那個地理節點的名稱（IT 只有一層，取根節點的「全國」）；自建帳號跟著代理的那位業務。
`catalog.USERS` 拿掉 `region` 欄，灌資料時由路徑算出來。

### 新欄位與新表

- `app_user.deactivated_at`：停用時間，NULL 是在職。
- `org_change_log`：`id`、`actor_id`（誰改的）、`action`（短代號）、`detail`（一句給人看的中文）、`created_at`。

## 主管端改看組織樹

主管端（`/manager`）開放給主管與 IT。三個分頁的「看得到哪些」統一成：**事情的當事人在我的組織範圍內**，
範圍用 `SHARING_LEVEL["manager_inbox"] = SELF` 截。主管的路徑只有三層、截不到 SELF，所以就是自己加屬下；
IT 是 `TW`，就是全公司。不再有任何一處用 `region` 過濾。

| 分頁 | 當事人 | 送給誰（通知對象） |
|---|---|---|
| 提問 | 提問者；自建帳號換算成代理的那位業務 | 不指定，範圍內的人都看得到、都能回 |
| 風險通報 | 拜訪的業務 `rep_id` | `manager_id` 記業務當時的直屬主管（拜訪結果頁顯示這個名字） |
| 簽核 | 申請人 `applicant_id` | 第二關 `user_id` 是申請人的直屬主管 |

- 簽核：主管的簽核匣是「指派給我、還沒簽的」。IT 的簽核匣是全公司還沒簽的，而且能簽任何一張；操作者記 IT 本人。
- 業務換主管時，他還沒簽完的出差單，第二關跟著改指派給新主管。已經簽過的不動。
- 灌資料時歷史出差單的簽核者改成申請人的主管，不再是「該區工號最小的主管」。

## 組織編輯

全部由 `services/org_admin.py` 執行，每個操作在同一個交易裡：檢查 → 改資料 → `rebuild_org_paths`（重算路徑與轄區並驗證整棵樹）
→ 跟著改待簽的出差單 → 寫一筆異動紀錄。檢查不過丟 `OrgError`，API 回 422 並帶中文訊息。

| 操作 | 規則 |
|---|---|
| 換直屬主管 | 對象是業務（停用的也可以，方便把人從要降職的主管底下移走）；新主管要是在職主管 |
| 主管調區 | 對象是主管；目標是區。屬下跟著走，他們的路徑與轄區一起重算 |
| 業務升主管 | 要選一個區；名下有客戶就要指定一位接手的在職業務，整批移交 |
| 主管降業務 | 底下不能有人（含停用的，否則樹會長到第五層）；要選新的直屬主管 |
| 新增帳號 | 名字、Email、初始密碼（至少 8 碼）、角色（業務／主管）與位置；工號接著最大號編 |
| 停用 | 不能停用 IT、自己、示範業務 U01；主管底下不能有在職的人；業務名下有客戶要指定接手的人 |
| 重新啟用 | 業務的主管已停用的話，先換主管 |
| 換客戶負責人 | 接手的要是在職業務 |

額外的護欄：

- **IT 帳號不能在畫面上改**，也不能把人升成 IT。最高權限只從 `catalog.py` 來。
- **示範業務 U01 不能改角色或停用**：所有自建與第三方登入的帳號都代理他（`EXTERNAL_ACCOUNT_ACTS_AS`）。
  他可以換主管。
- 停用的人**留在樹上原位**。他的歷史拜訪照舊給原團隊看；路徑一拿掉，那些紀錄就連 IT 都看不到了（`can_see` 對 NULL 一律拒絕）。
- 移交客戶只改 `customer.owner_user_id`。過去的拜訪、報價、出差單仍記在原本的人名下。

### 登入與停用

停用的帳號在 `start_session`（Email 與第三方登入共用）和 `user_from_token` 都被擋下，訊息「這個帳號已停用，請洽 IT」。
已經登入的裝置下一個請求就收到 401，前端照既有流程導回登入頁並顯示這句。

改角色不強制重新登入：權限每個請求都由後端讀資料庫決定，前端存的角色在下次打開 App 時由 `/api/auth/me` 更新。

## API

`/api/admin`，只有 IT（其他人 403）。每個寫入操作都回傳更新後的整張組織圖，前端直接換掉畫面。

| 方法 | 路徑 | 內容 |
|---|---|---|
| GET | `/org` | 地理節點、所有公司帳號（含停用的、名下客戶數）、最近 50 筆異動紀錄 |
| POST | `/users` | 新增帳號 |
| PUT | `/users/{id}/manager` | 換直屬主管 |
| PUT | `/users/{id}/unit` | 主管調區 |
| PUT | `/users/{id}/role` | 改角色（附新位置與接手的人） |
| POST | `/users/{id}/deactivate` | 停用（附接手的人） |
| POST | `/users/{id}/reactivate` | 重新啟用 |
| PUT | `/customers/{id}/owner` | 換客戶負責人 |

客戶 API 的 `CustomerItem` 多帶 `owner_id`，客戶檔案頁才知道目前的負責人是誰。

## 畫面

- **組織管理頁 `/admin`**（IT 的首頁）：依全國 → 區 → 主管 → 業務排成清單，停用的人淡色顯示。點一個人打開對話框，
  只列出他能做的操作；做不了的（例如主管底下還有人不能降職）不藏起來，而是寫出原因。上方「新增帳號」，最下面是異動紀錄。
- **主管端**：IT 進得去，標頭多一個回組織管理的按鈕。三個分頁的說明改成「你團隊」（主管）／「全公司」（IT），
  不再說「北區」。
- **客戶檔案頁**：IT 多一個「換負責人」按鈕。
- 角色顯示為「IT」；登入後依角色導向（業務 `/`、主管 `/manager`、IT `/admin`）；範圍說明的三句話補上 IT 的版本。

## 測試

新增 `backend/tests/test_admin.py`，組織異動的測試都在一條連線的交易裡跑、測完回滾，不影響其他測試用的假資料。

- IT 的路徑是 `TW`、轄區是全國；看得到任何客戶檔案，語意層查得到 250 家。
- `paths_from_reports` 拒絕：主管掛在根、IT 掛在區、業務的主管不是主管、第五層。
- 主管調區：屬下的路徑與轄區跟著變，代理 U01 的自建帳號轄區也跟著變。
- 換主管：待簽的出差單改指派給新主管，新主管的簽核匣看得到。
- 風險通報、提問、簽核只到直屬主管與 IT，同區的其他主管看不到。
- 停用：密碼登入與舊 token 都被擋；客戶移交給接手的人；U01、IT、有屬下的主管停不了。
- 升主管要指定接手的人；降職前底下要清空。
- 新增帳號後能用初始密碼登入，工號照順序編。
- 非 IT 打 `/api/admin` 一律 403；每個操作都留下異動紀錄。

既有測試裡用 M04 當北區主管的改回 M01。

## 部署

`models.py`、`services/org.py`、`catalog.py`、`generate.py` 都會改，`schema_version` 的指紋跟著變，部署時自動重建資料庫。
在畫面上做的組織異動會留到下一次重建為止，跟其他資料一樣。

## 不在這次範圍

- 共享層級表（`SHARING_LEVEL`）維持寫死在程式碼。
- 新增地理節點（區）。
- 寄信：新帳號的初始密碼由 IT 自己告訴對方。
