# 跟上次訂的一樣：照上次下單、出發前看促銷變了什麼

2026-10-07

業務每天照區跑那幾家店，多數客戶每個月進的東西都差不多。現在每次都要把十幾樣品項重講一遍，系統才開得出報價；
上次走了哪一口促銷、這期那一口還在不在、門檻有沒有變，也要業務自己去促銷頁比。這次讓業務講一句「跟上次一樣」
就照上次的單開這個月的報價，報價頁也能一鍵照上次填；客戶檔案先講清楚上次訂的哪幾項這期促銷變了；
報價成交後寫進交易紀錄，下一次的「上次」就是這一張。

## 為什麼做

- 系統記得每一張單（交易紀錄 `sales_transaction`、報價草稿 `sap_quotation_draft`），但畫面上沒有一處列出
  「上次那張單訂了哪幾樣」；客戶檔案只有上次進貨的日期。
- 拜訪錄音只認得業務講出來的品項，講「跟上次一樣」什麼都抽不出來。
- 促銷一個月一期，口會換、門檻會變；業務上次幫客戶下了中口，這期中口沒了，到了店裡才發現。
- 報價草稿開了就停在草稿，從來不會變成交易：成交了的報價還一直列在待處理事項，今日路線也一直當它是商機。

## 已定案的決定

1. **「上次訂的」兩邊都看**：上一次進貨（交易紀錄）與上一張報價草稿，比較新的那張為主，舊的那張只補新的沒有的品項
   （詳見下一節）。口只有報價記得。
2. **出發前的提醒只放在客戶檔案**：「進門前三分鐘」多一句摘要，加一區「上次訂的」逐列寫變了什麼。
   今日路線的小卡、首頁總覽、熊熊滾開口講這次不做。
3. **錄音由 AI 聽、後端展開**：AI 只判斷有沒有講「跟上次一樣」、哪些不要、哪些跟上次比加減；
   要抄哪幾列、這期對應哪一口、變了什麼，全部由後端照資料庫算（跟「進門前三分鐘」一樣不讓 AI 生數字）。
4. **促銷變了的列先抄上、標出變了什麼，不擋送出**：條件變了的口照新條件、口數不變；口沒了或促銷沒了，
   改成不走促銷、數量照上次付錢的數量。
5. **報價頁加「照上次填」**，跟錄音用同一份「上次訂的」。
6. **跟上次比的加減**（「再加一口」「魚油少 5 盒」「照上次」）由後端照上次的數量算。
7. **報價成交由業務按「客戶下單了」**：寫進交易紀錄與應收帳款，報價改成已成交（`ordered`）。不能復原。
8. **報價多一個狀態 `ordered`**：「上次訂的」算它；待處理事項與今日路線的商機照舊只看 `draft`。
9. **假資料**：最後一期促銷（決賽日 10/28 所在的 202610）做出三種變化；兩家客戶補上個月已成交的報價，不補交易。

## 「上次訂的」怎麼算

新的 `services/last_order.py`，客戶檔案、報價頁、錄音展開都呼叫它，數字只有一份。

### 取哪兩張單

- **上一次進貨**：這家最新的一張訂單（同一個 `order_no` 的品項；日期取最早的那天），每個品項 × 數量。
- **上一張報價**：這家最新的一張報價草稿，狀態是 `draft`、`pending_approval` 或 `ordered`，被駁回的不算；
  錄音回寫開的與報價頁開的都算。日期跟待處理事項一樣取拜訪時間、沒有拜訪取建立時間的當地日期；
  同一天好幾張取最後建的那張。每一列是品項 × 數量，或某一口 × 口數。

### 怎麼合

1. 兩張都沒有：這家還沒訂過（`null`）。
2. 比日期，新的那張為主、整張照抄；同一天以報價為主（報價有記口）。
3. 舊的那張只在兩張相差 **31 天以內**才拿來補（促銷一個月一期），太舊的不湊：
   - 舊的那張裡、新的那張沒有的品項，加上去；同一個品項兩邊都有，照新的。
   - **例外**：新的是進貨、舊的是報價，報價裡走口的品項，進貨也有時，拿掉進貨的那個品項，換成報價那個品項的每一列。
     真實流程是報價成交後才有交易，交易一定比報價新；不這樣做，口就被交易蓋掉了。
4. 列的順序：變了的列在前；其餘照來源，報價照列號、進貨照金額由大到小，為主的那張在前。

### 上次走口的列，跟這期比

先找這期的「同一口」：同一個品項、同名的那一口（名稱本來就把口寫在括號裡，例如「40EXa眼藥水(中口)」）。
同一個品項同名的有好幾檔（中化那種直走、9+1、17+3 都同名），照每口買的數量由小到大排，取同一個順位。

「條件」是每口買幾個、送幾個、每口售價、搭贈說明，四樣有一樣不同就算變了，變好也照實寫。

| 情況 | `kind` | 那句話（`text`） | 摘要用的短句（`short`） | 抄成 |
|---|---|---|---|---|
| 同一口還在，條件一樣 | — | — | — | 這期那一口 × 同口數 |
| 同一口還在，條件變了 | `terms` | 「從買 10 送 2 變成買 15 送 2，一口 $800 → $1,200」 | 「金舒胃平(小口)要買的量變多」 | 這期那一口 × 同口數 |
| 這一口沒了，同品還有別的口 | `pack_gone` | 「中口這期沒了，只剩小口（買 22 送 1，$3,080）」 | 「40EXa眼藥水(中口)沒了」 | 不走促銷，數量＝上次每口買的 × 口數 |
| 這個品項這期沒有促銷 | `promo_gone` | 「這期沒有促銷了」 | 「威鎮凝膠沒有促銷了」 | 不走促銷，數量＝上次每口買的 × 口數 |

- `terms` 那句：買幾送幾變了寫「從買 b 送 f 變成買 b′ 送 f′」，售價也變了接「，一口 $p → $p′」；
  只有售價變了寫「一口從 $p 變 $p′」；只有搭贈說明變了寫「搭贈改成「…」」。
  短句：每口買的變多寫「要買的量變多」、變少寫「要買的量變少」，其他寫「條件變了」。
- `pack_gone` 那句的口用括號裡的字（小口、中口、大口）；名稱沒有括號的用整個促銷品項名稱。
  剩下的口每一口寫「（買 b 送 f，$p）」，好幾口用「、」接。
- 現在沒有進行中的促銷：上次走口的每一列都是 `promo_gone`。
- 上次沒走促銷的列不比；「這期多了新促銷」這次不做。
- 抄成的結果裡，同一個品項不走促銷出現兩列（例如上次本來就有 40EXa 不走促銷 10 瓶，中口又換成不走促銷 57 瓶），
  併成一列、數量相加：報價不允許同一個品項不走促銷列兩次。

### 回傳的形狀

```
{
  order: { order_no, date } | null,   // 有用到的那次進貨
  quote: { quote_no, date } | null,   // 有用到的那張報價
  lines: [{
    sku, name, spec, unit,
    supply_price,                     // 這家的供貨價，報價頁加列用
    qty,                              // 沒走口是數量；走口是口數
    pack: { code, name, deal, buy_qty, free_qty, deal_price } | null,   // 上次走的那一口
    source: "order" | "quote",
    change: { kind, text, short } | null,
    repeat: { sku, qty } | { promo_code, packs }                       // 這次照抄成什麼
  }],
  changed: 3                          // 變了幾列
}
```

`GET /api/customers/{id}/last-order`：權限跟報價一樣（`SHARING_LEVEL["quote"]`，本人與主管），
別人的客戶回 404；沒訂過回 `null`。

## 資料

`models.py` 改了，`schema_version` 的指紋跟著變，部署時重建資料庫（跟以往一樣）。

- `QUOTE_STATUSES` 加 `ordered`（已成交）：註解寫「客戶下單了，已寫進交易紀錄與應收帳款」。
- `visit` 加 `repeat_last`（JSONB，可以是空的）：說了「跟上次一樣」或跟上次比加減時，展開那一刻的快照（見「錄音」）。
  存快照是因為這次拜訪確認後也會開一張報價，到時「上次」就變成這一張，確認頁會對不上。

### 假資料（`data/seed`）

**促銷的變化**只放在最後一期（`as_of` 所在的那一期，決賽日 10/28 是 202610），前幾期照舊。
`catalog.py` 加一份「最後一期的變化」，`build_promotions` 在最後一期套用；拿掉的口直接跳過，其他口的編號照舊。

| 品項 | 前幾期 | 最後一期 |
|---|---|---|
| 40EXa眼藥水 | 小口、中口、大口 | 只剩小口 |
| 金舒胃平(小口) | 販促搭贈<10+1>+1，買 10 送 2，$800 | 販促搭贈<15+1>+1，買 15 送 2，$1,200（每個一樣 $80） |
| 威鎮凝膠 | <11+2>+贈4盒AP磁力貼，$990 | 這期沒有 |

挑的是測試幾乎沒用到的品項：Premium 與骨營不動，報價、促銷頁、問答的測試都用它們這期的數字。

**上個月已成交的報價**：兩家，日期是 `as_of` 往前 28 天（9/30），狀態 `ordered`，單號照報價頁的格式
（`Q20260930-0001`、`-0002`），`created_by` 是負責業務；口用那天進行中那一期（202609）的編號，
金額照報價的算法（沒促銷照供貨價、不打折；口照每口售價 × 口數）。

## 客戶檔案

### 「進門前三分鐘」多一句

- `build_profile` 呼叫 `last_order`，有任何一列變了就寫：
  「上次訂的有 3 項這期促銷變了：40EXa眼藥水(中口)沒了、金舒胃平(小口)要買的量變多、威鎮凝膠沒有促銷了」。
- 短句超過 3 個只列前 3 個，後面加「等」。
- 排在「進貨間隔拉長」那句後面（沒有那句就排第一）；摘要最多 4 句的上限不變。

### 新的一區「上次訂的」

放在「下次去要記得」下面，跟它一樣自己讀 `GET /api/customers/{id}/last-order`，載不到只有這一區顯示失敗。

```
上次訂的                    10/5 進貨 · 9/30 報價
  40EXa眼藥水(中口) × 1 口
    ! 中口這期沒了，只剩小口（買 22 送 1，$3,080）
  金舒胃平(小口) × 3 口
    ! 從買 10 送 2 變成買 15 送 2，一口 $800 → $1,200
  威鎮凝膠 × 2 口
    ! 這期沒有促銷了
  魚油 30 入 × 32 盒
  人工淚液 15ml × 20 瓶
  …（沒變的最多先列 5 項）
  [ 再看 11 項 ]
  錄音時講「跟上次一樣」，就照這份開報價；促銷變了的那幾項會照上面寫的改。
```

- 右上角只寫有用到的那張（只有進貨就只寫「10/5 進貨」）。
- 變了的列全部展開，那句話用警示色，前面放 lucide 的警示圖示（不用 emoji）。
- 沒變的列最多先列 5 項，其他收在「再看 N 項」。
- 這家還沒訂過：只寫「這家還沒有訂過」。

### 待處理事項的「客戶下單了」

見「報價成交」。

## 報價頁「照上次填」

- 頁面最上面一個按鈕「照上次填（10/5 進貨、9/30 報價）」；`last-order` 是 `null` 就不顯示，載不到也不顯示。
- 按下去：
  1. 所有數量與口數清成 0。
  2. 照每一列的 `repeat` 填：`{sku, qty}` 填進常進品項、或促銷區那個品項的「不走促銷」；`{promo_code, packs}` 填進那一口。
  3. 頁面上沒有那一列的品項（例如這期沒促銷的威鎮凝膠），用回傳的品項資料與供貨價加在常進品項最後面。
  4. 變了的列下面寫那句話（跟確認頁同一個元件）。
- 填完還是業務自己按「開 SAP 報價草稿」；超過 20 列、折扣這些擋住的原因照現在。

## 錄音：「跟上次一樣」與跟上次比的加減

### AI 輸出

輸出格式在 `fields`、`sources` 旁邊多一個 `repeat_last`（不是拜訪的第七個欄位，不寫進 CRM）：

```
repeat_last: null | {
  all: boolean,            // 講了跟上次一樣、照上次、老樣子：照整張再下一次
  except_skus: [string],   // 這次不要的品項
  relative: [{             // 跟上次比的加減
    product_text, sku: string | null, promo_code: string | null,
    delta: integer         // 加減多少；口是口數。「照上次」是 0
  }]
}
```

- 結構化輸出要求物件的欄位全部明列，三個鍵都列進 `required`。
- `sources` 多一個 `repeat_last`，存原話（例如「跟上次一樣就好」）。

提示（`extraction.PROMPT`）多兩條：

- 業務講「跟上次一樣」「照上次」「老樣子」這類話，表示要照上次的單再下一次，`repeat_last.all` 填 true；
  說這次不要的品項（「威鎮這次先不要」）對照品項表放進 `except_skus`。
- 業務講跟上次比的加減（「再加一口小口 Premium」「魚油比上次少 5 盒」「人工淚液照上次」），填進 `relative`，
  `delta` 是加減的數量（照上次填 0），品項與口照第 7、9 條對；這些不要再填進 `intent`。
  講了確定的總數（「魚油這次 40 盒」）才填 `intent`。都沒講 `repeat_last` 填 null。

`all` 是 false、`except_skus` 與 `relative` 都是空的，當成 null。

| 業務說 | 抽出來 |
|---|---|
| 跟上次一樣就好 | `all` true |
| 跟上次一樣，魚油改 40 盒 | `all` true；`intent` 魚油 30 入 × 40 盒 |
| 老樣子，威鎮這次先不要 | `all` true；`except_skus` 威鎮凝膠 |
| 跟上次一樣，再加一口小口 Premium | `all` true；`relative` Premium眼藥水小口 +1 |
| 魚油比上次少 5 盒 | `all` false；`relative` 魚油 30 入 −5 |
| 人工淚液照上次，其他不用 | `all` false；`relative` 人工淚液 0 |

### 後端展開

在 `_extract` 清掉對不上的口之後（`relative` 的口也一樣檢查：不是這一期的口，那一項當成對不到品項）：

1. 用 `last_order` 算出上次訂的，每一列的 `repeat` 轉成下單意向的一項：
   `product_text` 是品項名稱或這期那一口的名稱，`unit` 是品項的單位或「口」。
2. `all` 為真才把整張放進來。
3. 拿掉 `except_skus` 裡品項的每一列（上次沒有的不理）。
4. 套 `relative`：在上次整張裡找同品項、而且同樣走口（有 `promo_code` 就找那一口）或同樣不走口的那一列，
   數量加上 `delta`。
   - 那一列已經在結果裡就改它，不在（`all` 是 false）就加進來。
   - 加完是 0 以下就拿掉。
   - 上次沒有這一列：`delta` 是正的就新增一列、數量是 `delta`；不是正的就不理。
   - 對不到品項的照第 6 步。
5. 業務講的絕對數量（`intent` 裡對得到品項的）：拿掉結果裡同品項的每一列，再加上它。
6. 對不到品項的（`intent` 與 `relative` 的）加在最後，數量留空，確認頁照現在標「缺少品項」。
7. 這家還沒訂過：下單意向只留第 5、6 步的，`error_message` 寫
   「說了跟上次一樣，但這家還沒有訂過，請手動填下單意向」（沿用現在顯示整理失敗原因的那一行）。

展開後的 `intent` 存進 `fields_raw` 與 `fields_final`（跟現在清掉口之後存的一樣）。
`field_sources["intent"]` 沒有原文時，用 `repeat_last` 的原話。

### 快照（`visit.repeat_last`）

```
{
  said,                         // 原話
  all, except_skus,
  order: { order_no, date } | null, quote: { quote_no, date } | null,
  empty: boolean,               // 這家還沒訂過
  changes: [{ sku, promo_code, text }],              // promo_code 是這次抄成的口，不走促銷是 null
  relative: [{ sku, promo_code, last_qty, delta }]
}
```

沒講跟上次一樣、也沒講加減，是 null。業務改逐字稿重新整理時，照新的逐字稿重新展開、快照重建。
`VisitDetail` 多回 `repeat_last`。

```
    ! 中口這期沒了，只剩小口（買 22 送 1，$3,080）
  金舒胃平(小口) × 3 口（買 15 送 2，$1,200）
    ! 從買 10 送 2 變成買 15 送 2，一口 $800 → $1,200
  Premium眼藥水(小口) × 2 口
    上次 1 口，這次多 1 口
  魚油 30 入 × 32 盒
  …
```

- 第一行只在 `all` 為真時寫；「這次不要」只在有 `except_skus` 時寫。
- 每一列用品項與口對快照的 `changes`、`relative`，對到就在下面寫那句話；業務刪掉那一列，那句話就不顯示。
  快照不跟著確認頁的修改變。
- 編輯、存欄位、送 SAP 的流程不變；送出後就是這個月的 SAP 報價草稿。

## 報價成交

### 畫面

- 客戶檔案「待處理事項」裡每一張 `draft` 的報價多一個「客戶下單了」按鈕；`pending_approval` 的按鈕反灰，
  旁邊寫「核准後才能成交」。
- 按下去先跳確認框：「把這張報價寫成今天的進貨？NT$ 23,000，會寫進交易紀錄與應收帳款，不能復原。」
- 成功後重新載入客戶檔案：那張報價從待處理事項消失，進貨數字、上次訂的跟著變。

### API

`POST /api/customers/{id}/quotes/{quote_no}/order`，權限跟報價一樣；回 `{ order_no, date, amount }`。

在同一個交易裡：

1. 把這張報價 `status = 'draft'` 的列改成 `ordered`；一列都沒改到就回 409「這張報價已經成交，或還在等簽核」
   （連按兩次也只寫一次）。
2. 寫交易（`sales_transaction`），日期是系統日 `app_today()`：
   - 單號 `SO{日期:%Y%m%d}-{客戶}-{報價單號}`，同一天成交兩張也不會撞號。
   - 一列報價一列交易。
     - 沒促銷的列：數量照報價，金額照這一列記下的金額（已打折）。
     - 促銷的列：數量是付錢的加送的（到貨的數量），金額照這一列記下的金額（每口售價 × 口數）。
   - 成本＝到貨數量 × 單位成本。
   - 上架費與通路獎勵＝金額 × 這家近 90 天的費率（近 90 天交易的上架費、通路獎勵各自除以進貨金額）；
     近 90 天沒有交易就是 0。
3. 寫應收帳款（`receivable`）：發票號碼＝單號，發票日＝系統日，金額＝這張的合計，到期日照付款條件
   （連鎖 60 天、獨立藥局與診所 30 天，跟假資料的付款條件同一組數字），還沒收款。

### 會跟著變的

進貨間隔、近 3 月進貨、帳齡與未收、今日路線（成交了就不再是商機）、問答查到的數字、下一次的「上次訂的」
（同一天的進貨與報價，以報價為主，口還在）。示範時在忠孝店按了，它的「進貨間隔拉長」可能就不見了，
要先講完那一段再按。

## 出錯時

| 情況 | 結果 |
|---|---|
| 說了跟上次一樣，但這家還沒訂過 | 下單意向只留業務講的，確認頁提示「說了跟上次一樣，但這家還沒有訂過，請手動填下單意向」 |
| 現在沒有進行中的促銷 | 上次走口的每一列都是「這期沒有促銷了」，抄成不走促銷 |
| `except_skus` 裡的品項上次沒訂 | 不理 |
| `relative` 減到 0 以下 | 拿掉那一列 |
| `relative` 的品項上次沒有，而且是減的或照上次 | 不理 |
| `relative` 的口不是這一期的 | 那一項當成對不到品項，標「缺少品項」 |
| AI 輸出格式不對、或展開時出錯 | 跟現在整理失敗一樣：欄位留白，顯示原因，讓業務手動填 |
| 業務改了逐字稿重新整理 | 重新展開，快照重建 |
| 照上次填超過 20 列 | 照現在報價頁的擋住原因 |
| `last-order` 載不到 | 客戶檔案那一區顯示失敗、可以重新載入；報價頁不顯示照上次填 |
| 成交時報價已經成交、還在等簽核或被駁回 | 409 |
| 別人的客戶 | 404（`last-order`、成交都是） |
